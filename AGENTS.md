# Agent Guidance

Guidance for coding agents working in this repository, including the automated Codex review that runs on every non-draft pull request. The contribution workflow is in [CONTRIBUTING.md](CONTRIBUTING.md).

## Working Agreement

- Update this file (`AGENTS.md`) as part of every change. Record the durable build, test, deployment, or debugging lesson the work produced, in the relevant section below. Keep it short and actionable; do not duplicate code or CONTRIBUTING.md.
- `install.sh` reads `.env.local` from the directory it runs in. Starting it from the wrong CWD (e.g. an isolated worktree without the production `.env.local`) makes it treat the tree as a **fresh install**: it apt-installs PostgreSQL 18, creates a new cluster + `openmaic` role/database, and writes a brand-new `.env.local` (fresh `OPENMAIC_SECRET_KEY`, throwaway `DATABASE_URL`, GitHub token from `gh auth token`). On 2026-11-15 this happened by accident and the fix-up was: `service postgresql stop && pg_dropcluster 18 main --stop`, `apt-get remove --purge postgresql-18 postgresql-client-18 postgresql-common postgresql-client-common`, remove `/etc/apt/sources.list.d/pgdg.list`, `userdel/groupdel postgres`, and delete the fresh `.env.local` and `.next` in the worktree — then re-run with the CWD set to `/kaggle/temp/KelasKA`. Always pass `workdir=/kaggle/temp/KelasKA` (or `cd` there) when running it, and if it starts installing system packages on a host that already has them, stop it immediately.
- After all work for a task is finished and verified, commit the changes and push them to `origin` on the current branch (Conventional Commit message), then report the branch, commit hash, and push result. Never leave finished work uncommitted; if the push is rejected or credentials are unavailable, say so explicitly instead of silently skipping it.
- Then deploy it: run `bash install.sh --colab` from the main checkout (`/kaggle/temp/KelasKA` on this host) once everything is committed. That is the production build + PM2 preset, so it rebuilds the standalone app and restarts it; a fix is not finished while the live site still runs the old build. Verify the changed surface and `pm2 logs kelaska` after it returns (the installer syncs `.next/static` and `public` into `.next/standalone` itself).

## Build and Test Resources

- Production-facing hardening landed in Nov 2026 audit: `/api/health` answers anonymous probes with only `{"success":true,"status":"ok"}` (a Docker/Compose HEALTHCHECK or the installer keep-alive needs just 200); the full diagnostic payload (exact `version`, `accessCodeConfigured`, `capabilities`, `parallelSceneConcurrency`) is served only with the `openmaic_access` cookie holding a valid access-code token, minted by `lib/server/access-token.ts` (`createAccessToken`). Tests in `tests/server/health-access-code.test.ts` pin the anonymous/authenticated shapes; the PBL v3 package test uses the literal `healthPath` string only.
- Internal design docs must never ship under `public/`. The `/wireframes/` product blueprint was anonymously reachable and exposed the full route/component/API inventory; it was moved to `docs/wireframes/` and later deleted at the operator's request. When adding a review/design artifact, default to `docs/`, not `public/` — the app serves everything in `public/` to anyone.
- `next.config.ts` sends `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `Permissions-Policy: camera=(), geolocation=(), microphone=(self)` (the voice features call `getUserMedia`) and `Strict-Transport-Security: max-age=31536000` on every route and sets `poweredByHeader: false`. Browsers ignore HSTS over plain HTTP, so pinning HTTPS still needs the zone-level "Always Use HTTPS" toggle in Cloudflare, which is an operator action, not a repo one — `install.sh` cannot set it either.
- The fork has no `/api/storage/upload` route (nor does self-hosted upstream); the hosted endpoint is upstream-hosted only. `lib/storage/client.ts#uploadBlobToStorage()` is a deliberate null-returning stub that keeps the PBL v2 callers' inline data-URL fallback instead of a guaranteed 404 POST on every image/PDF submission. Implement the route before restoring the fetch.

VoxCPM2 TTS is fine in Indonesian (a Gemini round-trip transcribed its sample exactly).
- Gemini free-tier quotas on the current key (RPM/RPD): `gemini-3.6-flash` and `gemini-3.8-flash` 5/20, `gemini-3.5-flash-lite` and `gemini-3.1-flash-lite` 15/500, `gemini-3.5-transcribe` 3/25, all TTS 3/10, every Nano Banana/image model **0** (free tier excludes image output), Gemini 3+ search grounding 0. - A narration batch is the one case where `PARALLEL_SCENE_CONCURRENCY=5` queues behind a single GPU: VoxCPM serves requests serially, so a five-clip batch spans ~8-40 s and clip five would die under the old 30 s `narrationClip` step deadline (“Gagal sintesis suara” in the UI). `STEP_DEADLINES_MS.narrationClip` is therefore 120 s, matching `TTS_REQUEST_TIMEOUT_MS`; raise it, do not parallelise the GPU.
- The python-api VoxCPM backend has no server-side voice registry (`POST /v1/audio/voices` is vllm-omni only) and synthesizes a fresh timbre on every call when given only a text voice prompt, so a course would narrate as five different teachers. Two call sites pin the narrator's timbre: `lib/server/generation/run/narrator-reference.ts` (the run engine) and `lib/server/agent-runtime/scene-tts.ts` (`synthesizeSceneNarration`, the agent's generate_actions/generate_tts path — it used to skip the pin entirely, so agent-built courses narrated each line as a different teacher). Both thread one bootstrap reference clip (cached per voice prompt in-process) as inline `reference_audio`; the adapter then sends the raw text instead of the `(design)` prefix. Cloning matches timbre, language-agnostic; Voices still need a matching `voiceDesign`/persona (id or en sample) for a gendered, consistent narrator. Verified 2026-11-14: without the reference the same sentence synthesizes at F0 ~205 Hz then ~253 Hz; with it, 204/208 Hz.

When adding a step, ask whether it depends on `node_modules`/the GPU result before serialising it; the background helpers (`GPU_SYNC_*`, `BOOTSTRAP_*`) print their log when joined and are killed by the exit trap.
- A rerun of `install.sh` on an unchanged tree skips `next build`: `jalankan_build` compares a fingerprint (git HEAD + `git status --porcelain` + baked `NEXT_PUBLIC_*` + `node_modules/.kelaska-build-packages.sha256` + Bun version + `--fast`) stored in `node_modules/.cache/kelaska/build.sha256`, then only re-syncs `.next/static`/`public` and restarts PM2. `--rebuild` forces it. The fingerprint deliberately invalidates on *any* tracked change (including docs/AGENTS), so a doc-only commit still rebuilds — do not "optimise" it with a pathspec unless the build actually stops depending on the file (traced runtime inputs like `skills/**` and `packages/@openmaic/generation/prompts-pbl/**` are copied into the standalone image).
- Do **not** run TypeScript parallel to the Turbopack compile in `install.sh`. It was tried (background `tsc -p tsconfig.build.json` with `OPENMAIC_SKIP_TYPECHECK=1` for Next, then a second incremental pass for fresh `.next/types`) and reverted on this 4 vCPU host: the background `tsc` read `.next/types/validator.ts` while Next was still writing `routes.js` (`TS2307: Cannot find module './routes.js'`) and the two processes oversubscribed the cores — 104-186 s versus 81 s with Next's own serial typecheck. Next builds its route types during compile, so no delay makes a concurrent `tsc` safe; keep the serial pass. PM2 `kelaska` is stopped before a rebuild (it serves `.next/standalone`, which `next build` rewrites in place) and the PM2 step starts it again.
- Do not run `bun install` and `scripts/build-packages.mjs`/`sync-interactive-assets.mjs` in the same tree concurrently while timing steps: the install re-links `node_modules`, and two `sync-interactive-assets.mjs` runs `rm -rf` each other's `public/vendor/interactive/<pkg>@<ver>` target, producing spurious `EEXIST`/`ENOENT`/`chmod` failures. They are safe to overlap only with genuinely different trees (that is what `install.sh` does with the docs build, which touches `packages/docs` and `public/docs-site` only).
- Maximize the RAM a memory-heavy Node task may use instead of leaving Node's default heap. The Next.js production build type-checks a large module graph and can exceed the default ~2 GB limit, failing with `FATAL ERROR: Reached heap limit`.
- Check `free -h` first, then size the heap from the host's RAM minus ~2 GB OS headroom — there is **no fixed 8 GB cap** on a big host. On this 31 GB host a single heavy task (full type check, production build, large suite) uses:
  ```bash
  NODE_OPTIONS="--max-old-space-size=30720" ./node_modules/.bin/tsc -p tsconfig.json --noEmit
  ```
  On the 12 GB Colab host the same rule gives `--max-old-space-size=10240` for `bun run build`. The cap is a ceiling, not a reservation, but size it so **one** task alone fits: do not run several memory-heavy tasks at once. When a merge verification genuinely needs two suites in parallel (merged tree vs base worktree), cap each at `--max-old-space-size=8192` and `--maxWorkers=2` so their combined worst case still fits the host.
- `install.sh` sizes the build heap as `min(30720, RAM - 2048)` MB (floor 1024), so this 31 GB host gets ~29 GB and a 12 GB Colab host 10 GB instead of the old 8192 MB cap. On Colab's 2 vCPU a Turbopack production build (`--build`/`--with-pm2`/`--colab`) dominates a cold run (~10-15 min) and Bun cannot speed it up; the installer's wins are building workspace packages two at a time and running model discovery alongside the build.

## Accounts

- The account layer is opt-in through `AUTH_ENABLED` (default off, so upstream and the test suite keep the anonymous owner). `--colab`/`--kaggle` writes it on **only when `DATABASE_URL` is set, the Supabase project is configured (URL + anon/publishable key, `NEXT_PUBLIC_*` included) and the Google provider answers `true` at `/auth/v1/settings`** — an enabled gate with no sign-in door would lock every visitor out of `/login`. `--with-auth` forces it on (explicit operator choice, same warnings), `--no-auth` forces it off. With it on, `ACCESS_CODE` is not consulted: `proxy.ts` answers 40x/redirect for every page and API except `/login`, `/api/auth/*`, `/api/access-code/*` and `/api/health`, and `app/api/access-code/status` reports the modal disabled so it cannot stack on `/login`. The installer probes the provider before enabling and blanks the dead `AUTH_GOOGLE_CLIENT_ID`/`AUTH_GOOGLE_CLIENT_SECRET` (and the earlier draft's `AUTH_ADMIN_PASSWORD`/`AUTH_ADMIN_NAME`/`AUTH_SEED_ADMIN`); `--auth-google-client-id`/`--auth-google-client-secret` no longer exist — re-running an old command line fails on the unknown flag. `--auth-public-url` stays, as the optional proxy origin for the sign-in redirects.
- The Edge proxy proves **authentication only** (signature + expiry of `kelaska_session`). Role routing and every authorization check read the database, so a role change applies on the next request instead of waiting for a new cookie. Do not put the role in the token.
- The host owner method lives in `lib/server/identity/host/session-cookie.ts` and registers from `instrumentation.node.ts` *before* the general owner check, with `anonymousFallback: false`. It resolves `user:<id>` and drops `OWNER_ANONYMOUS_PREMINT` itself. Moving that registration after owner resolution, or into `lib/server/identity/`, breaks the identity boundary test and lets an unsigned request become a fresh owner instead of a 401.
- `auth_users` / `auth_sessions` are provisioned by `ensureAuthSchema` inside `getServerPersistenceProvider`, and the tables are listed in `lib/persistence/schema-stores.ts`; add future auth DDL as a new migration, never by editing the baseline. Sessions store only the SHA-256 of the cookie's random id, so a database dump is not a set of replayable cookies; deactivating an account or deleting its sessions is an immediate revocation even though the cookie still verifies at the edge.
- Sign-in is Google-only **through Supabase Auth** (PKCE via `@supabase/ssr`; the Google client secret lives in the Supabase project, never in the environment). The login button calls `signInWithOAuth` with `redirectTo = <origin>/api/auth/supabase/callback` (the target must exactly match a Redirect URLs entry — no query string — so the post-sign-in deep link rides in a short-lived `kelaska_oauth_next` cookie that the callback validates with `safeNextPath` and clears); that route redeems the code with the browser-cookie PKCE verifier (`lib/supabase/server.ts`, a no-op `setAll` so the browser never receives Supabase tokens), maps the Supabase user via `lib/server/auth/supabase-identity.ts` (refuses no-email / unverified / no subject) onto the identity in `google-signin.ts`, and mints the app's revocable `kelaska_session`. `/login` gates the button on `supabaseBrowserConfigured()` (the `NEXT_PUBLIC_SUPABASE_*` pair baked at build time); the callback gates on `supabaseAuthConfigured()`. The Google `sub` is the identity: it is looked up first and bound to the row, and an address already bound to a *different* `sub` is refused rather than taken over. Requiring `email_verified` is what keeps an address an admin approved from being claimed by someone else, so do not drop that check.
- A new Google address creates a **pending** account (`active=false`, role student) and gets no session; the callback redirects to `/login?error=pending`. An admin approves and sets the role at `/admin` (the row's `CheckCircle2` button sends `PATCH {active:true}`, the edit dialog sets name/role). The bootstrap is `AUTH_ADMIN_EMAILS` (comma list, `AUTH_ADMIN_EMAIL` is the single form): those addresses are created as active admins on first sign-in, and an existing pending row for such an address is promoted on sign-in. With neither configured and no active admin, `bootstrap.ts` logs a warning at boot because nobody can approve anyone. Changing the address in `.env.local` alone does not help an account that is already pending: it stays pending until its next Google sign-in (there may be zero active admins until then). After swapping the address, edit `.env.local`, `HOSTNAME=0.0.0.0 pm2 restart ecosystem.bun.config.cjs --update-env`, then promote the already-bound row directly (`update auth_users set role='admin', active=true where email='<new-address>'`) so the promotion does not depend on someone signing in again (verified 2026-11-15 for ade781@dinas.belajar.id).

## Persistence and storage

- The course library is widened for administrators by the host `LibraryProvider` registered from `instrumentation.node.ts` (`lib/server/persistence-hooks/admin-course-library.ts`): when `AUTH_ENABLED` is on, the `admin` role lists every live course newest-first (capped at `MAX_LIBRARY_STAGE_IDS`), while every write stays owner-scoped. `summarizeLibraryStages` marks another owner's course `isOwner: false` in the `/api/stages` items (`LibraryStageSummary`); `listStages` carries that flag into `StageListItem`, and both the classic-home card and the workspace's `CourseCard` hide rename/delete/move/drag for it, while `WorkspaceShell` keeps such a listed course read-only (no stage-meta fetch or stranger redirect). A listed course with **no** flag is still assumed owned — that is why the widened list must set it. Non-admin accounts keep the owner-only list (no flag, so all courses look owned), and with accounts off the provider is not registered at all. Pinned by `tests/persistence/admin-course-library.test.ts`, `tests/persistence/host-library-provider.test.ts` (flag present for foreign, absent for own) and `tests/workbench/workspace-courses-page.test.ts` (foreign card has no ⋯/drag).
- Agent-created content must not land in the project folder. Course documents and jobs go to PostgreSQL; generated images, video, posters and narration go through `storeGeneratedAsset` (asset pool: PostgreSQL or the configured S3/HF S3 byte store); uploaded source files and extraction results go through `getMaterialByteStore`, which uses Hugging Face S3 when `HF_S3_*` is set. `data/` is left for the one-time legacy classroom import, local usage records and the global driver-model default only.
- `HF_S3_*` feeds two layers from one bucket: the `huggingface-s3` asset store (content-hash keys, registered in `instrumentation.node.ts`) and `lib/server/materials/s3-bytes.ts` (keys under `materials/…`). Keep `ASSET_S3_BUCKET` unset beside it. The namespaces cannot collide, so do not add a separate prefix or bucket unless the existing keys are migrated.
- Agent narration used to be written to `data/classrooms/<stage>/media` and referenced as `/api/classroom-media/...`; it now stores an `ast_` asset id in `audioId` (no legacy `audioUrl`). Playback and export resolve allocated ids pool-first, and the timeline's `audioExists` probes the pool after a local miss, so do not reintroduce a local-disk fallback for narration.

## Code Review Rules

### Severity

- P1 is only for problems that produce wrong behavior at runtime: user-visible breakage, data loss, data exposed across owners, an authentication or access-control bypass, a storage migration that fails on an existing database, a published package that ships broken, or a leaked secret.
- Inaccuracies that only affect documentation, comments, skill text or the PR description are at most P2. Do not report wording that cannot cause a failure or a wrong action.
- Do not report pure style, naming or readability preferences.

### Context and scope

- Read the PR description before reviewing. Do not raise an issue the description already accounts for (handled in another PR or issue, or a deliberate trade-off with its reason) unless you can show that explanation is wrong.
- Do not raise again an issue whose thread already has a reply explaining why it stays.
- When reviewing new commits, report only problems introduced or exposed by the new or changed code. Do not add edge cases on code the push did not touch.
- Do not report pre-existing behavior that the PR does not change.
- When a fix needs changes outside the PR (callers, documentation, other packages), name the file paths.

### Focus areas

- Owner scoping: reads and writes of courses, sessions, materials and settings stay within the requesting owner.
- Storage schema changes (`packages/@openmaic/storage`): compatible with databases that are already deployed.
- Published packages (`packages/@openmaic/*`): a change to published behavior comes with the version bump described in [Changing a Published Package](CONTRIBUTING.md#changing-a-published-package).
- Provider neutrality: shared layers do not hard-code a specific model or service vendor; vendor-specific behavior stays in that provider's module.
- Server-side requests to user-supplied URLs go through the existing URL guard.
